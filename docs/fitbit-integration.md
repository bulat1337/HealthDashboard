# Fitbit Air / Google Health

Раздел здоровья содержит общий переключатель человека и два вида: «Обзор»
(Fitbit Air) и «Состав тела» (существующие измерения Xiaomi). Обзор показывает
шаги, основной сон, пульс в покое и ночную HRV, график за 7/30 дней,
дистанцию, общие калории, минуты активных зон, стадии сна, SpO₂,
частоту дыхания, отклонение температуры кожи от базовой и тренировки.

Значения появляются только из реального аккаунта. Пропуск остаётся пропуском;
явный ноль сохраняется. Основной сон относится к локальному дню пробуждения.
Наличие отдельных показателей зависит от измерений и обработки в Google Health.
Стадии сна показаны отдельными временными дорожками по реальным `sleep.stages`.
Краткие пробуждения берутся из `shortAwakenings`, перерывы — из
`outOfBedSegments`, время до засыпания — из `summary.minutesToFallAsleep`.
Старый кэш с одними итогами продолжает показывать длительности до обновления.
Пустое поле сохраняется как неизвестное; переданный ноль отображается как ноль.

Пульс за день загружается через `heart-rate:reconcile` по локальному времени
наблюдения, с пагинацией и однодневными окнами. В кэше хранятся поминутные
средние, минимум и максимум, а также время в часовом поясе источника.
Цветные границы зон берутся из `daily-heart-rate-zones`; при их отсутствии
показывается обычная линия. Пропуски больше 10 минут разрывают линию.
Первичная загрузка охватывает то же окно, что и дневные данные (до 30 дней).
Обычные обновления перечитывают три последних дня; после длительного перерыва
восстанавливают окно синхронизации. Детальный пульс хранится за последние
31 день, дневные итоги — до года.

Шкалы качества сна сравнивают ночь с центральными 80% значений предыдущих
30 дней. Для каждого показателя нужны минимум 7 завершённых ночей с данными.
Это личный диапазон, отдельный от алгоритмов и норм приложения Google Health.
Оценка сна, его целевая длительность и готовые диапазоны качества отсутствуют
в используемой публичной схеме API и на сайте не генерируются.

Поля проверены по [официальной схеме Google Health v4](https://developers.google.com/health/reference/rest/v4/users.dataTypes.dataPoints).

## Что нужно для подключения двух браслетов

1. Google-аккаунт каждого человека, с которым он входит в Google Health.
   Нужны два адреса почты для сопоставления с профилями дашборда.
2. Один Google Cloud project с включённым **Google Health API** и OAuth client
   типа **Web application**. Скачать JSON этого клиента и сохранить вне репозитория.
3. Постоянный адрес дашборда для OAuth callback. На сервере и в Google Cloud
   должен быть указан один и тот же полный redirect URI:
   `https://your-dashboard.example/api/fitbit/oauth/callback`.
4. Каждый человек самостоятельно входит в свой Google-аккаунт и разрешает
   чтение выбранных групп данных через кнопку «Подключить Fitbit».

Пароли Google не нужны. JSON OAuth содержит client secret: хранить его
локально/на сервере, сообщать только путь к файлу.

## Телефоны

На iPhone и Android используется Google Health с соответствующим личным
аккаунтом. Перед подключением открыть приложение, проверить привязанный
браслет и дождаться синхронизации. Подключение сайта выполняется в обычном
Safari/Chrome через Google OAuth. HealthKit и Health Connect для этого пути
не требуются. Новые данные становятся доступны после синхронизации браслета
с приложением; сайт обновляет облачные данные каждые 15 минут.

## Календарь спорта

После успешной загрузки тренировок сервер автоматически сохраняет подходящие
занятия в календарь «Спорт» соответствующего человека. Учитываются бег (включая
дорожку и трейл), силовые тренировки, пилатес, йога, велотренировки и сап.
Сопоставление использует явный `exerciseType` из Google Health API и доступные
виды спорта. Ходьба, прогулки, походы и занятия без однозначного типа пропускаются.
Силовые без группы мышц записываются как «Силовая · всё тело».

Записи имеют метку Fitbit и раскрываются нажатием: время, дистанция, калории,
пульс и дополнительные доступные показатели. Полный полученный data point
сохраняется в `FitbitExercise.dataPoint`: круги, события, показатели и метаданные
доступны через «Все данные тренировки». Это поля записи `exercise`; отдельные
потоки GPS и посекундной телеметрии данным запросом не загружаются.
Схема полей: [Google Health — workouts](https://developers.google.com/health/data-types/workouts),
[Exercise reference](https://developers.google.com/health/reference/rest/v4/users.dataTypes.dataPoints#Exercise).

В файле спорта ручные записи остаются в `users.<id>.entries`, автоматические —
в `users.<id>.fitbitWorkouts`. Ключом служит ID тренировки в пределах человека.
Успешная загрузка заменяет свой диапазон дат: исправления и удаления отражаются
в календаре. При ошибке загрузки сохранённые тренировки остаются. История вне
окна обновления сохраняется независимо от срока хранения кеша Fitbit.
Перезапуск переносит уже закешированные тренировки. Начальная загрузка Fitbit
охватывает 30 дней, последующие обновления обычно перечитывают последние 14.

Ручные отметки и дистанции редактируются отдельно. Явная ручная дистанция дня
имеет приоритет при подсчёте километража; иначе суммируются все забеги Fitbit
за день. Больничный продолжает исключать день из стрика.

При запуске старые отметки `walking` заменяются на `run` с дистанцией 3.14 км,
остальные поля сохраняются. Перед заменой рядом с файлом спорта создаётся
`<SPORT_DATA_FILE>.before-walking-to-run.bak`. Новые отметки ходьбы API отклоняет.

## Google Cloud

- Включить Google Health API, создать Web OAuth client.
- Добавить точный redirect URI. Для локальной проверки подходит
  `http://127.0.0.1:5000/api/fitbit/oauth/callback`. Если используется 5001,
  заменить порт и в Google Cloud, и в `FITBIT_REDIRECT_URI`.
- На экране согласия добавить оба аккаунта в Test users на этапе проверки.
- Добавить read-only scopes:
  - `https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly`
  - `https://www.googleapis.com/auth/googlehealth.sleep.readonly`
  - `https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly`
- Приложение дополнительно запрашивает стандартные `openid` и `email`, чтобы
  проверить соответствие аккаунта профилю. Разрешения на запись не используются.
- У OAuth-приложения в Testing refresh token истекает через 7 дней. Для
  постоянного использования перевести приложение в In production с учётом
  требований Google к выбранному типу приложения. Проверка для публичного
  распространения и личное использование имеют разные условия; одного
  переключения статуса недостаточно для обещания публичного доступа.

Официальные инструкции: [Google Cloud и OAuth](https://developers.google.com/health/setup),
[правила запуска](https://developers.google.com/health/developer-checklist),
[совместимость устройств](https://developers.google.com/health/data-types/device-compatibility).

## Локальная конфигурация

Создать за пределами Git файл по образцу
[`fitbit-profiles.example.json`](fitbit-profiles.example.json).
`dashboardUser` должен точно совпасть с `id` пользователя из `/api/health-data`
(в текущем источнике это отображаемое имя). Каждому профилю нужен свой email.
Один email нельзя назначить нескольким людям.

Добавить в `.env.local` или environment-файл сервиса абсолютные пути:

```dotenv
FITBIT_OAUTH_CREDENTIALS_FILE=/absolute/path/to/google-health-oauth.json
FITBIT_PROFILES_FILE=/absolute/path/to/fitbit-profiles.json
FITBIT_REDIRECT_URI=https://your-dashboard.example/api/fitbit/oauth/callback
FITBIT_STATE_DIR=/absolute/path/to/private/fitbit-state
FITBIT_SYNC_ENABLED=true
```

По умолчанию состояние хранится в `~/.local/state/health-dashboard/fitbit/`.
Каталог создаётся с режимом 0700, файлы с токенами и историей — 0600.
Токены и email не возвращаются из публичного API и не попадают в клиентский bundle.
Защитить резервные копии состояния так же, как исходные файлы.

Перезапустить сервер, открыть дашборд по origin из `FITBIT_REDIRECT_URI`,
выбрать нужного человека → «Обзор» → «Подключить Fitbit».
Повторить для второго человека. В callback проверяются state, cookie,
PKCE, подпись/аудитория ID token, nonce и подтверждённый email. Аккаунт,
который не назначен выбранному профилю, будет отклонён.

## Обновление и API

- `GET /api/fitbit-data`: отдельные статусы и нормализованные данные всех
  пользователей. Пользователи берутся из существующего источника здоровья.
- `POST /api/fitbit/:userId/connect`: начало OAuth; проверяется origin,
  привязанный к настроенному callback. Возвращает URL согласия Google.
- `GET /api/fitbit/oauth/callback`: завершение авторизации, переход обратно
  в профиль выбранного человека. OAuth-коды не сохраняются.
- `POST /api/fitbit/:userId/refresh`: запускает фоновую синхронизацию;
  повторные запросы объединяются, ручной запуск ограничен одним в минуту.
- `/api/status`: содержит только профиль, статус и время обновления Fitbit.
- WebSocket `fitbit-data-updated` обновляет открытый обзор. При недоступном
  WebSocket клиент дополнительно проверяет статус, пока идёт синхронизация.

Первый проход загружает 30 дней. Следующие перечитывают последние 14 дней,
при длительном перерыве догружают до 30 последних дней. Кэш хранит до года
уже полученной истории. Автоматический проход запускается через 15 минут
после завершения предыдущего. `FITBIT_SYNC_ENABLED=false` отключает фоновые
проходы, сохраняя ручное обновление.

Используется стабильный Google Health v4. Активность агрегируется через
`dailyRollUp` в окнах до 14 дней; сон, тренировки и суточные показатели
читаются через `reconcile` с пагинацией и `google-wearables`.
HTTP 429/5xx повторяются с задержкой; потеря доступа требует повторного входа.
Сбой одного источника сохраняет его старый кэш и показывает предупреждение.
Успешно перечитанный источник заменяется целиком в своём диапазоне, поэтому
исправленная или удалённая запись не остаётся в локальной истории.

До выдачи OAuth credentials и разрешения обоих владельцев реальная
синхронизация остаётся непроверенной. Для тестов используются отдельные
временные файлы и ответы Google, без записи в личные источники.
